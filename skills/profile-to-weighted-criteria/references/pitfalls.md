# 实测踩坑清单

来自 Ai-get 项目把 L0 标准引擎从规则表换成 LLM 的实践。
每一条都有具体现象与实测数字，不是推断。

---

## 1. `expected` 的格式契约是全流程最脆的一环

**现象**：模型把 `size` 的 `expected` 写成「50 人以下」「50-200人」。
**为什么致命**：下游判定器按 `category` 分派后**直接解析**这个字段——
`size` 要 `split(":")` 成两个整数，`int("50 人以下")` 当场抛异常。

**修法**：
- prompt 里给**反例**而不只给正例（「不要写『50 人以下』」比「请写成 `0:50`」有效得多）；
- 入库前白名单校验，格式不对**就地降级**，不要让脏值流到远处崩；
- 契约表里明确写出「英文冒号」，中文全角 `：` 是真实发生过的错误。

## 2. 宽同义词表是一把双刃剑（最重要的一条）

**背景**：prompt 鼓励「同一含义多写几个同义词能显著提高命中率」。这对**召回**是好事，
对**打分**是灾难。

**实测**：一家法律咨询机构（未融资），简介原文是
「以合同合规与劳动用工为主业…通过线上**订阅**加线下顾问的模式服务长三角成长型企业」。

| 标准 | 规则引擎（token 为整句） | LLM（token 为 11 个同义词） |
| --- | --- | --- |
| 订阅制（w3） | 不确定 0.5 | **符合 1.0** |
| **总分** | **75** | **88** |

一个咨询顾问模式的合同措辞，因为命中了通用词 `订阅`，被判成「提供订阅制服务」。

**根因**：**单 token 子串命中 ≠ 语义确认**，而判定给了满分。

**修法**：判定因子要区分**命中强度**，不能只有三档：

| 强度 | 场景 | factor |
| --- | --- | --- |
| 强命中 | 多 token 同时命中，或命中专指性强的词（`按年付费`、`ARR`） | 1.0 |
| 弱命中 | 只命中一个通用词（`订阅`、`软件`、`服务`） | 0.5（不确定） |
| 无命中 | 文本里没有对应表述 | 0 |

**这条落在判定器，不落在生成器——换个更聪明的模型也不会自动修好。**

## 3. `temperature=0` 不等于可复现

**实测**：同一句画像、同一版 prompt、同一模型，连跑三次，产出的标准名不同：

```
行业：SaaS 软件服务
行业：SaaS与企业服务软件
行业：SaaS 软件公司
```

**后果**：
- **一个任务内部**是稳定的（结果冻结），这才是产品真正承诺的那部分；
- **两个用同一句输入的任务，标准不会一模一样**。缓存只在同一进程内掩盖差异。
- 如果标准的 `id` 由名字哈希而来（如 CRC32），名字一变 id 就变，前端按位置分配的颜色/状态会跳位。

**修法**：不要对外承诺「同样的输入永远得到同样的标准」。冻结 + 版本化 + 缓存能覆盖到的是
**任务级一致**与**成本可控**，不是**跨任务确定性**。

## 4. `lenient` 的默认行为会让分数虚高

宽松项的语义是「查不到 ≠ 不成立」，通常实现为「判『不确定』而不是『不符合』」。
但很多人顺手让「不确定」拿 0.5 分——**这就变成了「没证据也给一半分」**。

**实测后果**：一批 25 家里 19 家「待确认」，却仍有 6 家被抬进「明确符合」；
一家明显不符合要求的公司拿到 75 分。

**修法**：
- **未校验 = 0 分**，并让硬性维度不满足时**拦住「明确符合」这个结论**；
- 别用「归一化分母」之类的技巧绕——把未命中项从分母里去掉只会让分数**更高**（实测会到 100）。

## 5. 降级是静默的，必须留下痕迹

LLM 失败时回退到规则引擎，任务照样建得出来，只是标准质量不同。
如果不标出来，用户只会看到「这次的标准和上次不一样」，无从判断原因。

**修法**：把产出方冻结进任务记录——`criteria_source`（llm / rule）、
`criteria_label`（可读标签）、`criteria_fallback_reason`。

而且要区分两种「走了兜底」：

| fallback_reason | 含义 | 运维动作 |
| --- | --- | --- |
| **空** | 压根没试（开关是关的） | 想用就去开开关、填密钥 |
| **有值** | 试了但失败（如 `upstream: HTTP 502`） | 去查上游／密钥／配额 |

**空和有值是两种完全不同的动作，不能合成一个字段的语义。**

## 6. 白名单校验的粒度：逐条过、整批弃

- **逐条校验**而不是「要么全过要么全废」：一条越界的标准不该毁掉其余合理的标准。
- 但**通过数量不足时整批弃用**（实测阈值 2）：只剩一条标准时「加权得分」失去意义，
  还不如直接走兜底。
- 校验要覆盖：枚举成员、数值范围、**格式契约（见第 1 条）**、必填数组非空、
  以及**业务规则的强制值**（如「宽松项必须为 true」）。

## 7. 别把「模型名」当成想当然

产品宣传名 ≠ API 模型名。实测把宣传名直接传进 `model` 字段会得到
`invalid_request_error`，且响应体里会**列出真正的可用名**——
所以错误处理要原样保留服务端的错误消息（截断即可），那是排查时最有价值的信息。

## 8. 输出被截断是 JSON 模式最主要的失败原因

**现象**：解析失败，但报错只说「不是合法 JSON」，分不清是截断还是模型裹了话。

**修法**：
- 解析失败时把 **`finish_reason`** 一起写进异常：`length` 就是被 `max_tokens` 截断，
  这时该做的是调大上限，而不是去改 prompt；
- 附带**有界的内容预览**（取开头 160 字就够区分两种原因，不必整段进日志）；
- `max_tokens` 默认值给宽一点（4096 起步）：它是上限不是目标，正常输出用不到。

## 9. 绝不在判定时重新生成标准

判定阶段重新调 LLM 生成标准，会让①成本翻倍、②同一批结论前后不一致。
标准一旦生成就**冻结**，之后所有判定都用这一份。

「重新生成标准」应当是一个**用户显式触发**的动作（如「重跑挖掘」按钮），
把不确定性变成用户可控的选择，而不是藏在链路里。

## 10. 让「没接线的开关」大声失败

配置项被声明、被展示在状态接口里，却**没有任何代码分支读它**——打开它不会有任何效果，
却让人以为生效了。这比没有这个开关更坏。

**修法**：启用即打一条 warn 日志说明尚未实现；或者在文档里明确标注状态。
定期复查配置项与实际消费点是否一一对应。

## 11. 用户手写条件的「并入」逻辑会与 LLM 打架（最容易漏掉的一条）

画像之外用户还会手写几条判断条件。这些条件有**两条代码路径**：模型会尽力把它们写成标准，
而代码另有一套「规则识别 + 合并」的逻辑兜底。两条路径都在跑，**且没有任何校验比较它们**。

实测（画像「北京的 SaaS 企业服务公司」+ 条件「必须是一年内新成立的公司」「不接受人力外包型公司」）
暴露三个缺陷。**三条都不是模型的错，换更强的模型也不会自动修好。**

### 缺陷一：极性反转

用户写「**不接受**人力外包型公司」。代码的「行业族关键词」表里，`企业服务与软件` 族恰好含
「外包」二字，于是这条件被判成**该行业族的命中**，把 `外包` 并进了**正向**行业标准：

```
行业：企业服务与SaaS  →  行业：企业服务与软件（任一）
tokens: [… '软件', '云计算', …, '外包', '数据服务', …]
                              ↑ 用户明确要排除的词，进了「符合」的判据
```

**后果**：一家人力外包公司会因为简介里有「外包」而**符合** w=5 的硬性行业标准，
与用户意图完全相反。否定条件被当成了肯定证据。

### 缺陷二：整句当关键词

未被规则识别的条件会兜底成一条「业务特征：<原句>」的标准，并把**整句话**当单个 token：

```json
{"category": "business", "name": "业务特征：必须是一年内新成立的公司",
 "tokens": ["必须是一年内新成立的公司"], "lenient": true, "weight": 3}
```

它永远不可能在任何企业简介里被命中——是一条纯噪音：占一行条件、稀释权重、还让用户以为
这条要求已经在被检查。**而现有的校验器拦不住**：12 字 < 30 字上限，格式完全合法。
（这说明「关键词长度上限」只能挡住格式问题，挡不住「语义上根本不是关键词」的问题。）

### 缺陷三：契约里没有否定语义

输出契约没有任何字段表达「不符合则排除」。模型只能把否定条件写成**正向**标准，
于是 `question` 变成「公开资料是否显示公司主营人力外包…？」——命中即「符合」。
模型只好把真实含义塞进 `note`（「命中上述关键词即判定为非目标客户」），
**而判定器不读 `note`**。

### 修法方向

| 缺陷 | 修法 | 落在哪 |
| --- | --- | --- |
| 极性反转 | 用户条件**不要**再走「合并进已有维度」的启发式；极性信息必须显式保留 | 删除/重写用户条件的代码合并路径 |
| 整句当关键词 | 兜底时不要拿原句当 token；宁可只留 `question` 让它永远是「不确定」 | 同上 |
| 没有否定语义 | 契约加 `polarity`（`require` / `exclude`）或让维度支持 `negate`；判定器据此反转结论 | `contract.json` + `Criterion` + `judge.py` |

**共同根因**：同一句话被两条路径各自理解，理解不一致时代码那条赢了，且没有校验能发现。
这是「LLM 负责语义、代码负责结构」分工被打破的地方——**用户条件的解析属于语义，本该整条交给模型。**

完整实测样例见 `examples/valid/04-beijing-saas-user-conditions.json`（该文件带 `_observations` 注解）。

## 附：一次生成的真实 token 消耗

实测（`deepseek-flash`，契约 `criteria/v1`，2026-09-20，见 `examples/valid/` 各文件的 `provenance.measured`）：

| 场景 | 画像 | tokens |
| --- | --- | --- |
| 短画像（四个维度写全） | 杭州的消费品与旅游行业小微商家，员工 50 人以下… | 1776 |
| 短画像（只两个维度） | 深圳的跨境电商物流服务商 | 1667 |
| 短画像（信息量最小） | 上海的生物医药 CRO 企业，已完成 B 轮融资 | 1707 |
| 带用户手写条件（两条） | 北京的 SaaS 企业服务公司 + 两条条件 | 2413 |
| 带时间窗限定语 | 成都的环保科技企业，有过 A 轮融资，且近 6 个月内… | 1552 |

缓存命中时为 0。**调用次数与后续判定的记录数无关**——只花在「生成标准」这一步。

> 注意上表是**每次调用的 token 总量**（输入 + 输出）。同样是「短画像」，波动范围
> 约 1550~1780；带上用户条件后约 2400——多出来的部分就是 `conditions_block` 与模型为每条
> 条件多写一条标准。**不要把这些数字当容量规划的硬指标**，模型非确定性下它会浮动。
