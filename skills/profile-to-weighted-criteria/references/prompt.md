# 提示词快照与移植指南

版本：`criteria/v1`。

> **这是渲染结果的快照，不是真源。** 真源是两个文件：
> `prompts/criteria.system.md`（骨架 + `$占位符`）与 `contract.json`（维度枚举、上限、`expected` 契约）；
> 运行时会读它们并渲染出下面的文字（参考实现：Ai-get `server/app/llm/prompts.py`）。
> **要改提示词请改那两个文件，再重新取快照——直接编辑本文件不会生效。**

> **改 prompt 内容必须同步 bump 版本号**（即 `contract.json` 的 `version`）。标准会被冻结进任务记录，
> 只有知道「这批标准是哪版 prompt 产出的」，改了 prompt 之后历史结论才对得上。
> 版本号要连同模型名一起存进任务记录。

## 一、System Prompt（渲染结果，可直接复制）

下面这段由 `prompts/criteria.system.md` + `contract.json` 渲染得到，**与运行时实际发给模型的内容逐字一致**。

```text
你是 B2B 销售线索挖掘系统的「资格标准引擎」。
你的任务：把用户的一句客户画像，拆解成一组**可逐条判定**的加权标准。

只输出一个 JSON 对象，结构固定为：
{"criteria": [ {...}, {...} ]}

每条标准的字段：

- category：必须是这 6 个之一：geo / industry / size / funding / business / signal
- name：人类可读的标准名，格式「维度：取值」，不超过 22 个汉字
- question：该标准的判定口径，一句话，以问号结尾
- weight：整数 1-5。5 = 画像的骨架（地域、行业），3 = 明确写出的要求，1-2 = 锦上添花的偏好。
  参考默认权重：geo=5、industry=5、size=3、funding=3、business=3、signal=2、reachability=1
- tokens：字符串数组，用于与中文公开资料做**子串匹配**的关键词。
  必须是短的、真实可能出现在中文工商信息或企业官网里的词，**不要写句子、不要写描述**。
  同一含义多写几个同义词能显著提高命中率（例如「SaaS」写成 ["SaaS","saas","企业服务","软件"]）。
- expected：该标准的目标取值。**含义随 category 变化，必须严格遵守下表**。
- lenient：布尔。
- note：可选，一句话说明判定依据或所需数据（不超过 60 字）。

【各维度的 expected 与 tokens 契约 —— 下游判定器直接解析这些字段，写错会导致判定失败】

| category | tokens | expected |
| --- | --- | --- |
| geo | 城市名数组，如 ["杭州"] | 城市或区域名，如 "杭州" |
| industry | 行业关键词数组，如 ["SaaS","企业服务","软件"] | 行业名称，如 "企业服务与软件" |
| size | 必须是空数组 [] | **必须是 "最小人数:最大人数" 两个整数用英文冒号连接**，如 "0:50"、"50:200"、"300:1000000" |
| funding | 融资阶段数组，如 ["A轮"] | **必须是「未融资、天使轮、A轮、B轮、C轮」之一** |
| business | 特征关键词数组 | 必须是空字符串 "" |
| signal | 动作线索关键词数组，如 ["融资","中标","招聘","出海"] | 必须是空字符串 "" |

【硬性规则，违反即视为无效输出】

1. **不要凭空添加画像里没有的维度。** 画像没提地域就绝不要输出 geo 标准。
   宁可少输出，也不要为了凑数编造标准——编造的标准会污染整批判定结果。
2. 每个 category 最多一条；只有 business 与 signal 允许各最多 3 条。
3. **不要输出 reachability**，系统会统一补上。
4. **business 与 signal 的 lenient 必须为 true。** 理由：公开资料没写到某项特征，
   不等于这项特征不成立，把「没查到」当成「不符合」会让所有冷门行业集体掉档。
   其余维度的 lenient 一律为 false。
5. weight 达到 3 的是**硬性标准**——一旦判定为不符合，
   结论就不允许是「明确符合」。因此只有画像真正明确写出的要求才给 3 分及以上。
6. 时间相关的限定语（例如「近 6 个月完成融资」）用 business 承载：
   tokens 里放有助于在公开资料中检索到的词，并在 note 里写清需要带时间戳的数据才能验证。
7. 输出标准总数为 2~8 条。
8. **只输出 JSON**。不要解释、不要 markdown 代码块、不要注释。
```

### 为什么这几条规则长得这样

| 规则 | 不这么写会怎样 |
| --- | --- |
| 显式给出 `expected` 契约表 | 模型会写「50 人以下」这种人类友好但**机器解析不了**的值 |
| 「不要凭空添加维度」 | 画像里没提地域，模型也会贴心地补一条 `geo`，于是所有判定都被一条编造的标准污染 |
| `lenient` 的语义写进 prompt | 默认会把「公开资料没写到」当成「不符合」，所有冷门行业集体掉档 |
| 硬性阈值（weight ≥ 3） | 权重变成纯排序，失去「一票否决」能力 |
| 「只输出 JSON」 | 模型习惯性套 ```json 代码块，破坏 JSON 模式解析 |
| **排除 `reachability`** | 「能不能触达」与画像内容无关，是任何画像都通用的标准，应由代码统一补，不该让模型自作主张 |

## 二、User Prompt 模板

真源是 `prompts/criteria.user.md`，只有两个占位符：

```text
客户画像：
$query
${conditions_block}请输出 JSON。
```

渲染后的形态（`conditions_block` 有/无两种情况）：

```text
客户画像：
{一段自然语言描述}

用户手动补充的判断条件（每行一条，**必须全部纳入标准，不得省略**）：
- {条件 1}
- {条件 2}

请输出 JSON。
```

要点：

- **用户手写的条件必须全部纳入**，即使画像正文里已经隐含。模型漏掉的，由代码补齐后合并——
  「宁可重复一条，也不静默丢掉用户明确写下的要求」。
- 用户条件**没有**条件的场景就不输出这一段（`conditions_block` 退化成单个换行，
  不留一个空的列表头）。

## 三、迁到新领域：改这几处，别动那两处

把「潜客挖掘」换成别的筛选场景时：

| 必须改 | 落在哪个文件 | 说明 |
| --- | --- | --- |
| ① 维度枚举 `category` | `contract.json` → `categories[].name` | B2B 用 geo/industry/size/funding/business/signal；招聘可换成 城市/职能/年限/学历/技能/信号；供应商可换成 地域/品类/资质/规模/交付能力 |
| ② `expected` 契约 | `contract.json` → `expected_kind` / `enum_values` / `tokens_must_be_empty` | 与新枚举一一对应。**只要能机器判定的维度才允许进枚举** |
| ③ `lenient` 规则 | `contract.json` → `categories[].lenient` | 哪些维度「查不到 ≠ 不成立」要按场景重新判断 |
| ④ 权重表与各维度上限 | **不在技能目录**：规则引擎的 `CATEGORY_WEIGHTS` / `_MAX_PER_CATEGORY` / `_LLM_CATEGORIES`（Ai-get 在 `server/app/qualification/criteria.py`） | 跟着场景变，骨架维度给高权重。这几项与 `contract.json` 的一致性在加载时**逐项断言**，改一边忘另一边会直接起不来 |

改完 ①②③ 后：本节上面的契约表、以及 system 提示词里「每个 category 最多一条；
只有 X 与 Y 允许各最多 N 条」那条硬性规则，都由渲染器从 `contract.json` 自动跟随，**无需手改**。
最后别忘了 **bump `contract.json` 的 `version`**。

| 绝不能改 | 为什么 |
| --- | --- |
| ⑤「不要凭空添加画像里没有的维度」 | 这条是准确性的地基，换什么场景都成立 |
| ⑥「只输出 JSON」+ 白名单校验 | 结构化输出是「输出可校验」的前置条件，正则抠 JSON 不可靠 |

### 关于维度枚举的硬性要求

**枚举里的每个维度都必须能被现有数据判定。** 否则会出现「画像提了、模型也正确表达了、
但判定器判不了」的死路——这时应该做的是**补数据源字段**，而不是把标准删掉。

真实教训：`funding` 只能表达「融资阶段」，表达不了「**近 6 个月**完成融资」这种时间窗。
应当在 schema 里给维度加 `window`（时间窗）与 `judgeable`（能否用现有数据判定）字段，
让模型可以把「不可判定」当成一个**结论**输出，而不是默默降级成宽松项。

## 四、配套的调用参数

| 参数 | 建议 | 理由 |
| --- | --- | --- |
| `temperature` | `0` | 降低随机性（**但不等于可复现**，见 pitfalls） |
| `response_format` | `{"type": "json_object"}` | 结构化输出约束，优于「拿自由文本再正则抠」 |
| `max_tokens` | 4096 起步 | 它是**上限不是目标**，正常输出用不到。截断是 JSON 模式最主要的失败原因，留宽几乎零成本 |
| 缓存键 | `(prompt_version, model, 画像, 用户条件)` | 同样的输入不该重复问；**缓存只能省钱，不能替代「结果冻结」** |
| 超时 | 30s，超时即降级 | 外部依赖失败只应让标准「差一些」，不该让功能「不可用」 |

**调用次数预算**：生成标准是**每任务一次**，与后续要判定多少条记录无关。
如果把逐条判定也交给 LLM，成本会变成 `记录数 × 标准数`，高两个数量级——
所以判定应当尽量留给确定性代码，只把规则判「不确定」的那部分交出去。
