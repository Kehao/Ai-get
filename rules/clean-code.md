# 遵守 Robert C. Martin 的《代码整洁之道》(Clean Code)

本文件定义本仓库的强制性工作规则。在进行任何代码、测试、重构、审查或文档变更之前,遵循这些说明。

## 优先级与行为

- 将本文件中每一条不带限定的规则视为 `必须(MUST)`;将 `Prefer(优先)` 视为 `应当(SHOULD)`;将 `Do not(不要)`、`Avoid(避免)` 和 `Never(绝不)` 视为 `禁止(MUST NOT)`,除非用户明确覆盖。
- 优先考虑可读性、可维护性、正确性和安全变更,而非花哨或追求速度的技巧。
- 为下一个阅读代码的人类优化。
- 存在权衡时,选择能降低长期复杂度的方案。
- 绝不因为糟糕的结构已经存在就保留它。
- 应用童子军规则:让你触碰的代码比你发现它时更干净。

## 核心整洁代码原则

- 代码主要为人编写,而不只是为了执行。
- 保持代码简单、直接、易于修改。
- 避免偶然复杂度。
- 避免令人意外的行为。
- 优先显式意图,而非隐式魔法。
- 优先局部推理:读者应能以最少的跨文件跳转理解代码。
- 减少技术债,而非把技术债搬来搬去。

## 命名规则

- 使用能揭示意图的名称。
- 名称必须解释目的、角色或行为,无需额外注释。
- 避免误导性名称、过载含义和视觉上易混淆的标识符。
- 让区别有意义。不要创建仅在表面上有差别的名称。
- 使用可发音、可搜索的名称。
- 除非是成熟的领域或平台标准,否则避免缩写。
- 避免名称中的编码,包括类型前缀、实现提示和匈牙利命名法。
- 避免标识符中不必要的上下文。
- 当模块、类、命名空间或类型能提供上下文且比长名称更清晰时,用它们来补充上下文。
- 在代码库中,每个概念只用一个词。
- 不要为同一操作或概念使用多个同义词。
- 不要复用常见词汇来表达不同含义。
- 类、类型和模块名称应为名词或名词短语。
- 函数和方法名称应为动词或动词短语。
- 领域概念使用问题域名称。
- 技术概念使用解决方案域名称。
- 不要使用可爱、搞笑、晦涩或私人梗式名称。

## 函数规则

- 保持函数短小。
- 每个函数必须只做一件事。
- 函数应有一个明确的变更理由。
- 让每个函数保持在同一抽象层级。
- 自上而下组织代码,让读者先看到高层故事,再看细节。
- 优先描述性名称,而非简短名称。
- 最小化参数数量。
- 避免布尔标志参数。改为将行为拆分为独立函数。
- 除非语言惯例要求,否则避免输出参数。
- 消除隐藏的副作用。
- 区分命令与查询。
- 回答问题的函数不应同时修改状态。
- 根据项目语言规范,优先使用异常或显式结果类型,而非临时错误码。
- 将错误处理与主逻辑隔离。
- 积极消除重复。
- 优先直观的控制流,而非巧妙的控制流。
- 将深层嵌套重构为更清晰的结构。

## 注释规则

- 不要用注释来弥补糟糕的命名或结构。
- 先改进代码,再决定是否还需要注释。
- 优先自解释代码。
- 仅当注释能补充代码难以表达的信息时才使用。
- 好的注释类别包括:
  - 法律或许可要求
  - 非显而易见的意图
  - 重要警告或约束
  - 令人意外决策的理由
  - 对外部行为或协议假设的澄清
- 删除冗余、过时、显而易见、嘈杂和误导性的注释。
- 不要逐行叙述代码。
- 保持注释精确,并在代码变更时维护它们。
- 除非 TODO 注释是可执行的、具体的且必要的,否则避免。

## 格式化与结构

- 在仓库中保持一致的格式。
- 格式化代码以展现结构和意图。
- 让相关概念保持接近。
- 保持文件、类和函数合理短小。
- 使用垂直排序,从高层到低层讲述故事。
- 用缩进阐明作用域,而不是隐藏复杂度。
- 行过长伤害可读性时,避免过长行。
- 避免在编辑时易碎的装饰性对齐。
- 保持支持快速扫读的布局。

## 对象、模块与数据结构

- 有目的地区分富含行为的对象与纯数据载体。
- 不要随意混用数据容器与业务行为。
- 将实现细节隐藏在清晰的接口之后。
- 暴露行为,而非表示。
- 适当时使用类似 DTO 的结构作为简单载体。
- 避免火车失事式调用链和不必要的内部结构认知。
- 尊重松耦合和局部边界。
- 不要让持久化、框架和第三方细节掩盖业务行为或核心逻辑。

## 类与模块设计

- 保持类和模块短小。
- 每个类或模块应有一个主要职责。
- 倾向高内聚。
- 拆分累积了无关行为的类。
- 组织代码,使可能的变更保持局部性。
- 公共 API 应小、显而易见、难以误用。
- 优先组合而非复杂继承,除非继承明显是更简单、更稳定的模型。
- 不要让构造函数和初始化逻辑压过领域行为。

## 错误处理

- 有意设计错误处理。
- 让快乐路径易于阅读。
- 在错误消息中提供足够上下文用于诊断。
- 使用支持调用方决策的错误类型或异常类。
- 当存在更安全模型时,不要返回 `null` 或等价的存在性哨兵。
- 除非 API 显式建模该情形,否则不要传递 `null` 或等价无效状态。
- 根据代码库的语言和约定,优先使用异常、特例、空对象或显式可选性。
- 让资源清理和关闭路径正确且可见。

## 边界与外部依赖

- 可行时,将第三方库隔离在本地适配器或包装器之后。
- 避免将核心逻辑直接耦合到不稳定的外部 API。
- 围绕依赖创建窄接口。
- 为棘手的外部行为添加学习测试或有针对性的集成测试。
- 当依赖尚不存在时,从本地需求定义接口,而非猜测未来实现。

## 系统构建规则

- 将构建系统与使用系统分离。
- 让对象图装配、依赖注入、工厂和框架引导远离普通业务行为。
- 将启动接线放在显式 main 或组合区域。
- 当构建策略有意义或复杂时,使用工厂。
- 不要让横切关注点掩盖普通代码流。
- 仅当标准、框架、代理或 AOP 式机制能带来可证明的价值时才使用。
- 用可执行切片测试驱动架构决策,而非仅用图表或配置。
- 仅当领域特定语言比通用代码更能让系统意图清晰时才使用。

## 测试

- 将测试视为生产级代码。
- 保持测试干净、可读、确定、可维护。
- 一个测试应传达一个主要思想。
- 优先简单设置和清晰断言。
- 避免耦合到无关实现细节的脆弱测试。
- 测试应尽可能快。
- 测试应隔离且与顺序无关。
- 测试应自检。
- 为行为变更、bug 修复和重要重构添加或更新测试。
- 未经相应验证,不要交付代码变更。
- 修复 bug 时,在可行情况下添加一个本可捕获该 bug 的测试。

## TDD 与整洁测试规则

- 当行为能被清晰指定时,优先在生产代码之前编写失败测试。
- 不要编写超出失败测试或明确需求所证明的生产行为。
- 保持测试足够小,使失败能命名一个行为或一个概念。
- 当能提高清晰度时,每个测试优先一个断言或一个概念性断言。
- 使用能揭示被测业务或技术行为的测试名称和测试数据。
- 当重复设置隐藏意图时,构建小型测试词汇表或辅助 DSL。
- 保持测试代码干净;脏测试会降低安全变更生产代码的能力。
- 避免需要多个手动步骤才能运行的测试。
- 使用覆盖率模式发现未测试的风险,而非替代有意义的断言。
- 将被忽略、不稳定或跳过的测试视为未解决问题。

## 并发与异步工作

- 除非带来真实收益,否则不要引入并发。
- 当简单顺序代码足够时,优先使用它。
- 最小化共享可变状态。
- 优先不可变性、消息传递或清晰的拥有权边界。
- 让同步或加锁区域尽可能小。
- 对关闭、取消、超时和清理保持显式。
- 在重要的地方仔细测试并发行为。
- 修改并发代码前,先了解执行模型。
- 避免同步方法之间的依赖。
- 先让非并发行为正确,再添加线程。
- 当线程化代码的策略或并发级别可能变化时,使其可插拔、可调。
- 在可行时,让并发敏感测试在多种线程数、调度和平台下运行。
- 在证据说明并非如此之前,将偶发失败视为可能的并发缺陷。

## 重构规则

- 以小而安全的步骤重构。
- 改善结构的同时保持行为。
- 先让它工作,再让它正确。
- 消除重复、死代码、误导性抽象和特例杂乱。
- 名称薄弱时积极重命名。
- 当提取能改善内聚和清晰度时,提取代码。
- 内联不再值得其成本的抽象。
- 优先通过所有相关测试的最简单设计。

## 涌现设计与持续改进

- 优先运行所有相关测试、消除重复、表达意图并使用最少数必要类和方法的系统。
- 通过工作草稿完善代码,而非期望第一版就是干净的。
- 当代码起步粗糙时,持续改进名称、结构和测试,直到意图清晰。
- 当增量改进能安全恢复设计时,不要开始大规模重新设计。
- 对触碰的代码应用童子军规则,但让清理与任务规模成比例。

## 需要检测并消除的坏味道

触碰代码时,主动查找并修复以下问题:

- 含糊或误导性名称
- 重复逻辑
- 过大的函数
- 过大的类或模块
- 混合抽象层级
- 隐藏副作用
- 布尔控制标志
- 过长参数列表
- 深层嵌套
- 应被隔离或多态的过多条件
- 应被重构而非堆注释的代码
- 死代码和未使用的抽象
- 脆弱测试
- 无必要的环境依赖测试
- 不必要的间接层
- 偶然复杂度
- 使变更广泛扩散的耦合
- 需要多于一个手动步骤的构建或测试
- 错误抽象层级的代码
- 依赖派生类的基类
- 穿过对象内部的中转导航
- 无关概念之间的人为耦合
- 隐藏逻辑依赖
- 未实现的显而易见行为
- 错误的边界行为
- 被覆盖的安全机制
- 没有具名含义的魔法数字
- 掩盖意图的否定条件
- 被忽略的测试和不足的边界测试
- 读者须先理解算法才能信任其名称的函数

## 变更流程

对每个非平凡任务:

1. 理解意图和受影响行为。
2. 识别最简单正确的变更。
3. 先改进名称,再添加注释。
4. 尽可能保持编辑局部化。
5. 按需添加或更新测试。
6. 运行相关验证。
7. 审查 diff 的可读性、重复和不必要复杂度。
8. 确保最终代码比以前更干净。

## 实现偏好

- 优先显式、平淡、可维护的方案。
- 优先标准库和现有项目模式,而非新依赖。
- 除非依赖明显降低整体复杂度,否则不要添加。
- 复用既有项目约定,除非它们与这些规则冲突或用户明确要求其他方式。
- 保持接口小。
- 保持状态转换显而易见。
- 避免过早优化。
- 只有存在证据或已知需求时才优化。

## 审查清单

结束前,验证以下全部内容:

- 名称揭示意图。
- 函数小而专注。
- 类和模块职责清晰。
- 注释必要且准确。
- 错误处理显式且有用。
- 合理处已消除重复。
- 测试恰当地覆盖变更行为。
- 代码从上到下读起来干净。
- 设计比以前更简单,或至少没有更复杂。
- 变更遵循现有项目约定。

## 输出预期

进行变更时:

- 简要说明改了什么。
- 说明运行了哪些测试或检查。
- 指出任何未解决的风险、假设或权衡。
- 如果请求的变更与这些规则冲突,遵循用户请求,但显式提及该冲突。

## 硬性规则

- 不要引入误导性名称。
- 没有强理由不要保留重复逻辑。
- 不要在更好的代码能消除需求的地方添加注释。
- 没有强理由不要混用查询与变更。
- 不要悄悄扩大超出所请求任务的范围。
- 不要让触碰的代码比之前更难读。
