# company_discovery：实体发现 agent

配置驱动的实体发现 agent：**一句画像进去，一批补全后的档案出来**。

```
① 检索网页  →  ② 提炼实体  →  ③ 逐级深挖补全
```

**位置**：`server/app/agents/company_discovery/`（开发阶段随项目运行；
模块刻意零内部依赖，成熟后整体拷出、补 `pyproject.toml` 即可独立）。
跨 agent 共享的能力在 `app/agents/common/`。

## 快速开始（项目内）

```python
from app.agents import run_project_discovery

run = run_project_discovery("近 6 个月完成融资的 SaaS 公司")
for step in run.steps:
    print(f"{step.action:<8} {step.target:<20} {step.detail}")
for dossier in run.matched:
    print(dossier["name"], "|", dossier.get("domain"), "|", dossier.get("summary"))
```

`run.steps` 是完整的执行轨迹：

```
search                    检索「近 6 个月完成融资的 SaaS 公司」，拿到 20 条网页
extract                   认出 12 个公司，初判符合画像 4 个
deepen   领健              补全 5 个字段（0 → 5/7）
deepen   硅基流动           补全 5 个字段（0 → 5/7）
deepen   Flock集团          补全 0 个字段（0 → 0/7），仍缺 domain、summary、…
```

## 精确工作流程

### 第 1 步 · 检索（1 次搜索调用）

**输入**：`query`——默认就是画像原文，不拼不改写（87 字节）：

```json
{ "query": "近 6 个月完成融资的 SaaS 公司", "top_k": 20 }
```

**动作**：调一次搜索（本项目＝百度千帆智能搜索，纯搜索模式，`top_k=20`）。
前端「结果数量」选择框会折算 `top_k`（≤20，百度 v2 单次检索的源上限）与
提炼轮数——更大的档位靠多轮提炼榨同一批网页，最终行数如实回填。

**输出**：20 条原始网页（65 KB，每条含 title/url/content/website/date 等 18 个字段；
链路实际只使用 title/url/content/website/date 五个）。
以领健为例，它在这一步被发现的来源是第 5 条：

```json
{
  "url": "https://www.taihecap.com/transaction_show-9-575.html",
  "title": "领健Linkedcare完成D轮融资,泰合资本担任独家财务顾问",
  "date": "2026-03-18",
  "website": "北京泰合鼎诚投资咨询有限公司",
  "content": "…领健成立于2015年…正在为3万多家口腔、医美机构提供SaaS管理软件…（445 字正文）"
}
```

### 第 2 步 · 提炼（1~3 次模型调用，每批 5 家，零页面抓取）

**输入**：画像原文 + 第 1 步网页的**前 16 条**（每条正文截 260 字，合计约 66 KB）。

**动作**：**分批多轮**——每轮一次模型调用、最多认 5 家**新**实体
（「已找到名单」随轮次喂回去让模型避重），最多 3 轮。每轮做三件事——
  1. 认出网页里提到了哪些实体（**含媒体页里的**，不做"像企业站就收"的过滤）
  2. 按字段表填轻字段（简介/行业/地区/融资阶段，读不到就留空）
  3. 按画像逐条核对，给出 `matched` 初判与依据

每轮产出经 `on_batch` 回调立即交给调用方——智能发现列表**落一批行、前端显示一批**，
不必等全部提炼完。某轮不足 5 家或两手空空就提前收场（模型自己表示「榨干了」）；
单轮调用失败重试一次，再失败带着已有批次收场，不让一次波动清空全场。

为什么拆批：一次要 10+ 家 × 20 字段，输出预算（8192 tokens）经常撞
`finish_reason=length` 整批截断——每轮 5 家输出小而稳。

**输出**：候选清单 5~15 家（批次数 × 每批 ≤5）。**本步填充的企业字段**：`name`（初名）、
`matched` 初判、`reason`；部分候选能顺带带出 `industries` / `location` /
`funding_stage`（若正文前段提到）。领健在其中长这样：

```json
{
  "name": "领健Linkedcare",
  "domain": "",
  "evidence_url": "https://www.taihecap.com/transaction_show-9-575.html",
  "matched": true,
  "reason": "消费医疗SaaS，2026年3月完成D轮融资"
}
```

（`domain` 空是因为依据页是财务顾问官网，不是企业官网——拿不准就留空。
这一步**零页面抓取**，用的是搜索接口自带的正文，所以快；全文抓取留给第 3 步）

### 第 3 步 · 深挖（对挑中的每一家，默认 3 家；以领健为例，21 秒）

**输入**：画像 + 该家名字（第 2 步给的，可以是简名）+ 同一批网页 + 现有域名（可空）

依次执行：

1. **筛材料**：只留「标题或正文包含公司名」的页面
   → 领健这次入选的是泰合交易页、36氪报道（2 份）
2. **抓这些页面的全文**（每页 2500 字；抓不到保留搜索给的摘要）
3. **定位官网**（仅当还没有域名）：检索一次「<名> 官网」→ 每条结果取注册域、
   对照跳过清单（搜索引擎/百科/社交/媒体/招聘/工商目录）→ 第一个没被跳过的域名
4. **抓官网首页**（2500 字）
5. **整理**：材料 + 画像 + 名字 → 模型按字段表输出完整档案
   ——名字可能在此升级为工商规范全称（从官网或材料读到）；
   **本步补全**：`domain` / `summary` / `industries` / `location` / `funding_stage`
6. **补缺循环**（最多 `max_gap_rounds` 轮，默认 1）：档案的 `missing` 里有必填字段 →
   取第一个，按它的 `search_hint` 拼检索词（如「<名> 公司规模」）→ 抓前 2 页 →
   再整理一遍

领健这次的真实产出（699 字节，完整档案）——注意名字从简名升级为工商规范全称：

```json
{
  "name": "江苏领健智能科技有限公司",
  "domain": "linkedcare.cn",
  "summary": "为口腔等消费医疗机构提供AI+SaaS数智化管理软件、耗材采购平台及隐形正畸解决方案。",
  "industries": ["口腔智能化解决方案", "消费医疗数智化管理软件", "SaaS"],
  "location": "江苏",
  "employees": "", "funding_stage": "D轮", "founded": "",
  "matched": true,
  "reason": "口腔SaaS公司，材料显示其完成D轮融资",
  "missing": ["employees", "founded"]
}
```

**停止条件（任一命中即停）**：`missing` 清空（字段齐了）；本轮检索一无所获；
补缺轮数用完。

> 上面是**深挖 v1** 的流程，保持原样留档。v2 只在 L2 与 L3 之间插入一步「L2.5 官网子页探索」，
> 见下文「精确工作流程 · 深挖 v2」；`budget.max_subpages` 设 0 或抓取器不提供 `fetch_links` 时，v2 自动退回 v1。

### 各步填充的企业字段（领健实测）

字段是**逐段累积**的——②给初名与初判，L1 给正文，L2 给官网（最大增量），
L3 按缺口定向补。空格表示该步没拿到，留给下一步。

| 字段 | ① 检索 | ② 提炼 | ③ L1 抓已知页 | ③ L2 官网 | ③ L3 路由 |
| --- | --- | --- | --- | --- | --- |
| `name` | 原料 | ✓ 初名 | — | — | — |
| `domain` | 原料 | 偶有 | — | ✓ 定位 | — |
| `summary` | 原料 | — | ✓ | ✓ | ✓ |
| `industries` | 原料 | △ | ✓ | ✓ | ✓ |
| `location` | 原料 | △ | ✓ | ✓ | ✓ |
| `employees` | 原料 | — | — | △ 子页 | ✓ 招聘路由 |
| `funding_stage` | 原料 | △ | ✓ | — | ✓ |
| `founded` | 原料 | — | ✓ | △ 子页 | ✓ |
| `latest_funding` / `investors` | 原料 | ✓ 正文核心 | ✓ | — | ✓ |
| `products` / `business_model` | 原料 | — | ✓ | ✓ 官网 | — |
| 工商类（`legal_rep` / `registered_capital` / …） | 原料 | — | △ 爱企查页 | — | ✓ |

读法规矩：**空格不是失败，是"留给下一步"**——这正是缺口驱动循环的设计本意。领健这轮的结局：规模和成立时间没补到 → `missing` 如实保留 → 收工。

### 一次 run 的调用账（默认配置，挖 3 家）

| 调用 | 次数 | 花费 |
| --- | --- | --- |
| 搜索（本项目＝百度千帆） | 1 + 最多 3 家 × 2 = **最多 7 次** | ≈ 0.25 元 |
| 页面抓取（HTTP 直连目标站，不经搜索） | 最多 6 + 3×(1+2) ≈ **15 次** | 免费 |
| 模型调用 | 1~3 次分批提炼 + 每家 1~2 次整理 ≈ **5~9 次** | 几分钱 |
| 总耗时 | | 60~120 秒（分批提炼略增，但第一批 5 家几十秒即可见） |

## 精确工作流程 · 深挖 v2（L2.5 官网子页探索）

v1 的实测短板：首页常常只有简介，**成立时间、联系方式这类信息住在子页里**——
领健的 `founded` 在 v1 就是这么漏掉的。v2 的思路：官网子页抓取**免费**（HTTP 直连），
所以插在花钱的 L3 之前——子页能补上的缺口，就不必再花检索的钱。

**触发条件（三者同时满足）**：首轮整理后 `missing` 非空 ＋ `budget.max_subpages > 0`
（默认 3）＋ 抓取器提供 `fetch_links`（可选扩展，不提供就静默跳过、退回 v1）。

以领健为例（v1 同款输入：画像 + 「领健Linkedcare」+ 同一批 20 条网页 + 空 domain，
真机 37.1 秒，比 v1 的 21 秒多出子页与一轮整理）：

1. **L1 / L2 与 v1 完全一致**：筛材料 → 抓已知页全文 → 定位官网 → 抓首页
   （领健这次 L1 抓 6 页、命中 2 页，L2 定位到 `linkedcare.cn`）
2. **首轮整理**（与 v1 相同）：产出第一版档案
3. **L2.5 · 抓首页链接**：抓 `https://linkedcare.cn` 的 HTML，抽 `<a href>`
   → 解析成绝对 URL、剔掉锚点/脚本/邮件协议、按出现顺序去重
   → **输出 16 条候选链接**
4. **L2.5 · 挑子页**（三道闸，纯函数 `pick_subpages`）：
   - **同注册域**：`linkedcarefuture.com` / `linkedsmile.com` / `agentcare.com`
     （集团兄弟品牌）被剔，`saas.linkedcare.cn` 这类子域保留
   - **非资源文件**：`.png` / `.pdf` 等后缀剔掉
   - **关键词打分**：路径命中「关于/产品/招聘/联系/新闻」词组记分，同分路径短在前
   → 挑中 3 条：`about-us.html` / `contactus.html` / `business-license.html`
5. **L2.5 · 抓子页正文**（每页 2500 字，材料追加进材料池）
6. **二轮整理**：同一份提示词再整理一次。领健这次的增量——
   `founded: "2015年"`（关于页）、`official_contact: "客服热线400-900-5198；邮箱contact@linkedcare.cn"`
   （联系页）、`english_name: "Linkedcare"`
7. **L3 照旧**：仍缺 `employees` → 检索「领健Linkedcare 公司规模」→ 抓百科 + BOSS直聘
   → 最后一轮整理（v1 逻辑原样保留）

**v2 最终档案（相对 v1 的差异）**：

| 字段 | v1 | v2 | 来源 |
| --- | --- | --- | --- |
| `founded` | ❌ 没补到 | **2015年** | L2.5 关于页 |
| `official_contact` | ❌ | 客服热线 400-900-5198 | L2.5 联系页 |
| `english_name` | ❌ | Linkedcare | L2.5 |
| `missing` | employees、founded | **只剩 employees** | |

`employees` 两个子页都没有 → 留给 L3 → L3 也没抓到 → 如实保留。**缺口驱动的设计在 v2
里不变，只是「免费的子页」排在了「花钱的检索」前面。**

### v2 的调用账（相对 v1 的增量，每家实体）

| 调用 | 增量 | 花费 |
| --- | --- | --- |
| 页面抓取 | +1 次首页（拿链接）+ 最多 `max_subpages`(3) 个子页 | 免费 |
| 模型整理 | +0~1 次（首轮已填满则 +0） | 几分钱 |
| 搜索 | **不变**——L3 仍在，但缺得少时会更早停 | — |

抓取轨迹实录（12 次 = L1 6 页 + 首页 + 3 子页 + L3 2 页，L1 里抓不到的 4 页也如实计入）。

### 企业 logo：确定性直取，不进字段表

深挖成功定位官网后，抓取层会顺手抓一次 logo（`fetch_icon_url`）：候选顺序
apple-touch-icon → `rel=icon` → `og:image` → 根目录 `favicon.ico`，**每个候选都先做
轻量校验（200 + image/*）才返回**——给前端一个坏地址比不给更糟。拿到后以 `logo` 键
盖进档案，落行时写入 `TargetCompany.logo_url`，前端「所属公司」列用它替换字母角标
（加载失败回落字母）。

**logo 故意不写进 `fields` 字段表**：材料是纯文本，模型读不到图片也读不到 HTML 头部
的 `<link>`，写进去它只会对着正文编一个 URL。这是「抓取层直取、模型不碰」的字段，
与字段表那套「LLM 按材料抽取」的纪律分属两路。

### 各步填充的企业字段（v2 新增列）

| 字段 | ③ L2.5 子页（v2 新增） |
| --- | --- |
| `founded` | ✓ 关于页（v1 的痛点在这补上） |
| `official_contact` | ✓ 联系页 |
| `products` / `business_model` | △ 产品页（本次首页已覆盖） |
| `employees` | △ 招聘页（领健官网无招聘入口，落到 L3） |

## 三个协议

| 协议 | 你提供什么 | 失败时 |
| --- | --- | --- |
| `WebSearch` | 网页检索 | **抛异常** |
| `PageFetcher` | 把一个网页抓成文本（可选扩展 `fetch_links`：抽页面链接，v2 子页探索用） | 返回空串 / 空列表 |
| `JsonLlm` | 要求返回 JSON 的对话补全 | **抛异常** |

都是 `Protocol`——不需要继承任何基类。`JsonLlm` 已内置 OpenAI 兼容实现
（`OpenAiCompatibleLlm`，覆盖 DeepSeek / Moonshot / 通义 / vLLM / Ollama）。

> ⚠️ 检索失败**要抛异常，不要返回空列表**。返回空会让调用方把「搜索服务挂了」
> 误读成「市面上没有这类公司」。抓取器相反：失败返回空串就行，它只是补材料。

## 配置

`configs/company_discovery.json`：

| 键 | 说明 |
| --- | --- |
| `entity` | 实体类型的中文说法，只影响提示词措辞 |
| `fields[]` | **字段表，唯一的语义来源**（现有 20 个，含打分所需的全部字段） |
| `budget` | 各项上限：`max_entities` 挖几家（成本主开关）、`max_pages` 抓几页、`max_gap_rounds` 补几轮、`max_subpages` 官网子页探索抓几个（v2，设 0 退回 v1） |
| `query` | 检索用的查询，留空＝直接用画像原文（推荐） |
| `site` | 限定检索站点，留空＝全网 |
| `skip_hosts` | 追加要跳过的站点（注册域形式），用于「找官网」那一步 |

`fields[]` 每一行同时决定四件事：**提示词里的字段说明、`missing` 白名单、定向检索词、
输出形状**。加一个字段只需要改 JSON，四处一起跟上。

### 三条纪律

**① 没有落点的字段不要写进 `fields`。** 抽出来了却没处存，等于白花检索费
（`founded` 曾因「能挖到、没处存」白花了一阵）。

**② `required` 是花钱开关，不是「重要性」标注。** 只有 `required: true` 的字段会驱动
补缺检索。默认配置里全部为 `true` 是为了与旧行为一致；想省钱就把次要字段改成 `false`
——它们照样会被尽力抽取，只是不再触发花钱的补缺。

**③ `search_hint` 写检索词，不要直译字段名。** `domain` 要的是「官网」而不是「域名」。
写错不会报错，只会让那一轮检索白跑。

## 宿主集成（Ai-get 项目侧）

agent 本体只认三个协议；以下是宿主（`server/app/repositories/targets.py` 等）怎么用它：

- **智能发现**：检索 + 分批提炼在后台线程执行，每批 5 家落一批行、前端表格逐批显示
  （骨架占位）。前端「发现数量」档位（10/20/30）折算检索条数与提炼轮数
  （`_agent_search_plan`）；深挖入口在勾选行后的气泡框（批量逐个深挖，行级栅格化）。
- **深挖完成的回写**（`_apply_dossier` / `deep_dive_company`）：行名升级为工商规范名
  （legal_name 优先）、`logo_url`、官网联系方式状态置就绪，并按同一份 L3 规则标准
  **重判**刷新综合结果与匹配分。
- 详情面板只读展示深挖状态与档案字段；所有深挖按钮都在表格列与勾选气泡框里。

## 边界与已知特性

- **不含搜索实现**。搜索请由宿主提供（本项目在 `adapters.py` 里接的百度）。
- **不做并发**。实体逐个深挖，简单、可预算、便于观察。
- **判定会波动**。同一批材料，模型两次给出的 `matched` 可能不同——
  它适合「跑一次拿一批候选给人看」，不适合当确定性数据管线。
- **260 字的信息边界**。提炼只看搜索摘要的前 260 字——正文后段的信息
  （客户规模、产品清单）要等深挖抓全文才拿得到，这是两段信息量的分界线。
